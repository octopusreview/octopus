# Background error triage

Sentry is the platform error destination for terminal hosted review failures and repository indexing failures. Organization Slack notifications continue to be sent.

Error-event breadcrumbs retain known categories, levels, timestamps and validated HTTP methods and statuses, but omit messages, URLs and arbitrary data. Background failure events omit breadcrumbs entirely. Transaction and streamed-span hooks remove known request headers, bodies and query fields, sanitize URL-shaped names and attributes, and apply the breadcrumb policy to transactions. The same span policy applies to legacy standalone span payloads at envelope delivery. Envelope headers and newly generated sampling contexts also sanitize URL-shaped transaction names, including inherited names at Sentry delivery. This is a bounded policy: arbitrary free text, other path-based identifiers and inherited baggage forwarded to other services are not covered. Treat propagated trace data as a separate privacy boundary.

In the Octopus Sentry project, filter Issues by:

```text
environment:production error_boundary:background -synthetic:true is:unresolved
```

Check new and regressed issues daily. Start with recurring failures that affect reviews. Each event includes failure stage, ownership (`platform`, `organization` or `unknown`), provider and a safe code; its context also records retryability (`transient`, `permanent` or `unknown`). Only generation-stage provider failures are classified: HTTP 401, 402, 403 and 429 belong to the owner of the key used; a platform-key 429 and HTTP 500, 502, 503, 504 and 529 are transient, and a 5xx is platform-owned only on a platform key; interrupted streams, connection resets, body timeouts and `ETIMEDOUT` are transient with ownership unknown; `UND_ERR_HEADERS_TIMEOUT` has unknown retryability and is not retried automatically; invalid requests, refusals, an organization-key 429 and cancellation are permanent. Everything else, and every other stage, stays `unknown`. See [review coverage](review-coverage.md) for generation retry conditions; the event is reported only for the terminal failure. Its `background_failure` context carries the available repository/PR identifiers, revision, attempt ID and retry count. The attempt ID identifies a review attempt, an index attempt (including pre-review indexing), or a queue job when the outer worker catches the failure; it does not guarantee a saved review-attempt record. Correlate the affected work with authenticated Review Logs or repository indexing logs using the available context. Link the fix and verify the deployed version before resolving the issue. Unknown means the available evidence does not establish the cause; it is not a confirmed provider outage.

Repository indexing log reads return at most the latest 500 entries in chronological order; older entries are omitted when the log exceeds that limit. This reader does not report whether truncation occurred, so the viewer always warns that saved messages may be incomplete. Saved entries and live events can appear more than once when their identities are ambiguous; the viewer warns about possible duplicates. Writes are best effort and read failures return an empty list. The live viewer buffers up to 1,000 tagged messages while checking their attempt and warns when messages may be missing; this is not durable backfill. Untagged live messages are sanitized and shown immediately with an attribution warning. The viewer displays up to 200 messages at a time with controls for older and newer messages, but retains the accepted list in memory without a bound. While viewing an older or paused page, use the refresh control if the messages in that range change. If dropped messages exceed attribution tracking for 1,000 attempts, the warning remains for that repository view. These limits count entries, not bytes.

This version reads the legacy `${ELASTICSEARCH_INDEX_PREFIX}_repo_sync` index by default and reads `${ELASTICSEARCH_INDEX_PREFIX}_repo_sync_attempts` when the persisted marker matches the active server attempt. It also reads the attempt index when the marker matches the current local upload and either there is no active attempt or the upload's batch matches it. User and admin APIs, current legacy writers, and the viewer preserve approved fixed and numeric progress messages; other log text is withheld because it may contain sensitive details. Severity and timestamp remain available. It still writes and cleans up only the legacy index; the legacy cleanup race remains, so logs may be mixed or missing. Older workers may broadcast sensitive live messages, so upgrade and drain them before exposing this viewer. The marker migration must be applied before this reader is deployed; check the actual database migration ledger for failed and pending migrations first. Before rollout, verify attempt-index mappings, reader and writer permissions, and retention. Deploy compatible readers everywhere and drain older writers before a later release switches writes to the attempt index. Roll back only to a reader that understands both formats. No attempt-index writer or retention policy is introduced in this phase.

Older backend responses can still carry raw saved-log payloads during a mixed-version rollout. Deploy the sanitizing version and drain old workers before treating network payloads as protected. Indexing-stage review failures use generic outward messages while structured diagnostics retain safe metadata. Indexing failure notifications use generic messages instead of the underlying error.

The optional `indexing_deadline:worker_25m` tag identifies the worker's own 25-minute abort, not the dependency that delayed indexing. An untagged `TimeoutError` has an unknown source.
On worker-deadline events, `indexing_last_milestone` may identify the last allowlisted indexing log milestone observed by that attempt. It is a clue, not proof of the active operation or cause; `not_recorded` means no recognized milestone was observed. The tag contains no log text, file paths or progress counts and is available only after the change is deployed.

Review startup and preparation failures use generic messages in hosted review outputs and persisted status; logs retain safe diagnostics rather than underlying error text. Best-effort preparation failures likewise log safe diagnostics and retain their existing fallback. For review preparation failures, the optional `preparation_operation` tag distinguishes `review_input` fetches from `repository_tree` fetches. GitHub tree failures can also be grouped by their HTTP status code, for example `failure_code:http_451`. These identify the failed boundary or upstream response, not its cause or a confirmed fix; response bodies are not included in the event.

Hosted generation failures without a recognized provider or admission error and publication failures also use stage-specific generic messages. Post-generation failure logs retain safe diagnostics rather than exception text. GitHub review-creation errors retain the HTTP status, not the response body. Hosted review retains its existing summary-only fallback after inline failures; OSS bot posting uses that fallback only for HTTP 422.

Provider failures use a generic message instead of the provider's error text. The offline local-agent case retains its instruction to run `octp agent serve`. Available safe diagnostics include the provider, key owner, HTTP status and allowlisted error code; raw provider responses and causes are not included.

An embedding failure while preparing search context fails the review with a generic message. Best-effort feedback matching and review or diagram storage failures retain the review outcome; their logs contain only safe diagnostic fields, not the underlying error text.

`PROVIDER_REFUSAL` identifies an Anthropic response explicitly marked as a refusal when the expected text or tool use is absent. It does not by itself establish a provider outage or customer recovery.

Explicit credit/spend blocks, confirmed cancellations, superseded work and non-actionable capacity refusals do not create background incidents. Terminal failures on an organization-owned credential are still retained, now labelled `failure_owner:organization` when the status is 401, 402, 403 or 429; this can increase event volume and includes expected key rejections. Review cancellation is distinguished from queue expiry using the execution deadline; deadline failures remain reportable. Existing queue retries report only at exhaustion. Handled review failures are already terminal and report immediately, after the single generation retry where one was admitted. This does not claim every swallowed exception elsewhere in the application is covered. Local CLI uploads and community/legacy large-review pipelines are outside this change.

After a release, an operator can run `node apps/web/sentry-smoke.mjs --send-synthetic` inside one review-worker container with its existing Sentry configuration. It sends one labelled synthetic event through the shared reporting helper and prints its event ID and release. Verify that event in Sentry, including its release, stage and safe context, then resolve the separately grouped synthetic issue (`synthetic:true`). A successful flush alone does not prove receipt. This check never calls a model or changes customer data, and is not exposed as a web endpoint. Self-hosted deployments remain opt-in through their existing DSN configuration.
