# Review coverage and incomplete results

A completed job is not necessarily a complete PR assessment. Octopus records which changed text hunks it actually supplied to the reviewer, separately from findings and quality scores.

## Standard review input

The reviewer enumerates provider file metadata before allocating its model-input budget. GitHub file pagination is independent of the raw diff ceiling, so a large early fixture cannot erase the paths or patches of later source files. GitLab diff metadata and Bitbucket diffstat are paginated too. The provider revision is checked before and after fetching; changed head/base revisions abort the attempt instead of mixing input revisions.

Source, configuration and package/build scripts have priority over test fixtures and documentation. Whole files that fit are supplied first; remaining space can contain complete hunks from a larger file. There is no character cut through a hunk. File and hunk digests and ranges are retained in the coverage manifest. Each supplied hunk records `sha256` over its exact emitted text (including its hunk header and normalized trailing newline); `suppliedSha256` hashes the entire emitted file section, while `patchSha256` hashes the provider patch or the recovered patch described below. Unresolved provider patch omissions and mismatched hunk/change counts stay explicit.

Existing `.octopusignore` exclusions are recorded as repository policy. Curated default generated-file exclusions remain explicit. A repository's additional generated labels cannot silently hide source, tests, schemas or configuration; those remain accounted for. Excluded files are not claimed as reviewed.

### Missing GitHub added-text patches

When the files API omits a patch, GitHub input acquisition can recover a complete newly added ordinary text file from the full PR diff. Recovery requires mode `100644`, a safe unquoted path, an unambiguous section, a zero old blob, and a new index prefix matching the full inventory blob SHA. A single complete added-file hunk must match the explicit addition/deletion counts. Reconstructed content preserves Unicode, CRLF and terminal-newline semantics; its Git blob SHA-1, computed with its UTF-8 byte length, must equal the full inventory SHA. See the [recovery implementation](../apps/web/lib/github-text-patches.ts) and [regressions](../apps/web/lib/__tests__/github-text-patches.test.ts) for exact evidence checks.

Recovery never replaces a present empty, malformed or null API patch, or a provider patch discarded by retention. Modified, renamed and removed files, unsupported paths or modes, binary/NUL content, ambiguous sections, missing or contradictory metadata and truncated hunks cannot qualify. Recovered patches consume the same per-file and cumulative source/supporting acquisition allowances and the [review allowance](#limits-and-follow-up-work); revision and inventory-count checks still apply. Recovery supplies eligible input, not a score or a guarantee of complete coverage for a large PR.

### Declared binary asset policy

Policy `github-binary-assets-v2` records qualifying GitHub binary assets as **excluded, content not reviewed**, while keeping their paths in the changed-file inventory. The supported extensions and recorded kinds are:

| Extensions (case-insensitive) | Asset kind |
| --- | --- |
| `.png`, `.jpg`, `.jpeg` | Image |
| `.ttf`, `.woff2` | Font |
| `.zip` | Archive |

This is an explicit text-review scope: images and fonts are not decoded or inspected, and ZIP archives are not opened or scanned. Their contents may include source or executable code and have not been reviewed for safety. A Git binary declaration can also result from diff attributes; it does not prove that a file is valid media, a valid archive, or inherently nontextual. A supported extension alone never authorizes exclusion. A supplied text patch under any of these extensions remains eligible text.

The declaration must be an unambiguous, complete raw-diff section for an added or modified same-path file with regular non-executable mode `100644`. The adapter checks the exact old/new paths, status, explicit zero addition/deletion counts, and a hexadecimal new-blob prefix of at least seven characters against the full GitHub blob SHA. Any present API patch (including empty, malformed or null), patch-retention error, missing metadata or conflicting declaration prevents this exclusion. Renames, copies, deletions, executable files, symlinks, submodules and mode-only changes are outside this policy. Other binary extensions remain unavailable. Paths must use unquoted ASCII letters, numbers, dots, underscores, hyphens and single directory separators, without `.` or `..` segments. An uninterpretable raw-diff header prevents binary exclusions for that input rather than risking an ambiguous path match.

The GitHub adapter shares the raw-section parser with text recovery and binds each qualifying declaration to its provider, head/base revisions, path, status and blob SHA. Shared preparation revalidates the policy version, asset kind, binding and raw-section SHA-256 before retaining evidence in the immutable coverage manifest. Existing revision-drift checks still apply. Excluded assets contribute zero supplied characters and zero hunks; their exclusion does not establish model assessment of the remaining text. An excluded-only change uses the existing no-model disposition and receives no numeric quality score.

Historical `github-binary-png-v1` receipts remain valid only for their original PNG scope. Preparation retains their exact receipt shape and PNG exclusion reason without upgrading their version or rewriting old attempts. New acquisitions emit v2 receipts, including for PNGs. The evidence remains in coverage JSON; this policy requires no database migration.

This binary policy does not alter text acquisition or other providers. A source patch that remains missing after [added-text recovery](#missing-github-added-text-patches), or exceeds acquisition retention, stays unavailable and blocks complete coverage unless an existing explicit repository policy already excludes it. Source marked `-diff` through Git attributes remains subject to this requirement. This policy adds no ignore patterns or configuration switches and does not change severity thresholds or assessment-completion requirements.

Excluding an asset does not exclude supplied source that processes it. A finding grounded in reviewed extraction or serving code can mention an excluded archive; an assertion that the archive is absent merely because it was not supplied is unsupported. The [excluded-input guard](#claims-about-excluded-input) preserves this distinction within its documented limits. Complete eligible input and a valid model assessment are still required for an overall score; broadening asset scope does not resolve text-budget omissions.

## Assessment completion and request provenance

Supplied files alone do not establish a completed assessment. The final provider adapters report completion state and capture SHA-256 receipts over their actual SDK request payloads, after model-prefix, caching, thinking and text transformations. Each receipt records whether all requested message contents survived the transformation. The attempt retains these receipts, the selected model, policy/template digests, response-text digest and completion outcome; it does not publish raw prompts, credentials or private source.

The [covered-review request builder](../apps/web/lib/review-request.ts) replaces unpaired UTF-16 surrogates with U+FFFD in system instructions and the assembled user message before dispatch; valid surrogate pairs, including emoji, remain intact. `inputPreserved` therefore compares the repaired message, not the original malformed text. OpenAI-compatible adapters also apply this repair for callers that bypass the builder. OpenAI Responses repairs both instructions and input while keeping omitted instructions distinct from an empty string.

A passing assessment requires a completed provider response, preserved request input and a valid report with its canonical score table and findings JSON. Empty, malformed, token-limited, interrupted, unknown-completion or unobserved responses stay incomplete and cannot publish category or overall scores or a successful native check. Useful findings remain available. Legacy/local bridges without underlying completion evidence stay unknown. Explicitly excluded-only input records a no-model disposition; it does not claim an assessment of the excluded content. Identical immutable retries remain idempotent; changing request, policy or outcome evidence conflicts with the original attempt.

Input completeness and assessment validity are independent: `coverage.complete` records whether the eligible changed input was supplied, while `coverage.assessment.state` records the response disposition. Both are required for an assessed result. With complete input and an invalid or unavailable assessment, the report says **Input complete; assessment invalid or unavailable**, retains a specific structural reason, removes every category and overall score, and fails the native check. A recorded provider failure during generation instead identifies **review generation failed**; the attempt retains safe diagnostic fields with classified failure ownership and retryability (unknown when the cause is not established), and the comment and failed check show the allowlisted failure code beside the attempt ID. Capacity receipts no longer store the provider's request identifier; older attempts keep what they recorded.

A hosted review may retry generation once (two provider requests in total, with SDK retries disabled on this path) when the first request fails with a `transient` classification; unknown causes, organization-key rate limits, refusals, invalid requests and cancellation are not retried automatically. The retry starts only if at least 180 seconds of generation plus the 60-second publication reserve remain in the original job after the provider's `Retry-After` delay, or one second if no delay is available. Immediately before the second request the reviewer rechecks the PR head and request version, cancellation, organization access, the credential route, credits, the monthly cap and the low-balance guard, and claims one unit of a durable budget of two generation dispatches per PR request version, so a redelivered or re-enqueued job cannot start a third. If any check fails the original failure stands. The measured complete-review path keeps its own 600-second minimum, so it retries only when that still fits. Each earlier failed attempt is kept under `assessment.attempts` with its failure evidence and request receipt; completeness is evaluated on the final attempt. After a retry that is interrupted as well, the comment and check say **Review generation was interrupted twice and was not completed. No score was produced.** with the attempt ID and, when available, failure code.

A failed generation attempt is never charged: it is recorded as a `review-failed-attempt` usage row with unknown tokens, hidden from the customer usage views. A successful generation is charged once per PR, request version and head through a unique charge key; a later generation for the same key is not debited and adds no usage row. Large-review delegation, community reviews, CLI/local reviews and the follow-up findings call are unchanged. Interrupted provider calls and presentation corruption do not rewrite input coverage. Older immutable attempts retain their original recorded values.

The [system prompt](../apps/web/prompts/SYSTEM_PROMPT.md) owns the exact score format for complete and incomplete input. Intentional withholding of a score is valid only for incomplete input; summary and findings validation still apply. New assessment receipts record `responseValidation` independently of `completion`, actual request provenance and input coverage. A valid response with observed provenance and completed provider execution can retain assessment state `completed` over incomplete input, but `reviewAssessmentComplete` remains false and the check fails. Its reason identifies the withheld score and incomplete input. Malformed findings, missing provenance and incomplete or unknown provider completion remain failures, with concurrent diagnostic causes retained.

For score-table compatibility, the [assessment parser](../apps/web/lib/review-assessment.ts) accepts escaped Markdown pipes in notes and spaces or tabs around the slash in otherwise valid integer scores. An odd run of backslashes escapes a pipe; an even run leaves a cell separator. Required-category uniqueness, score range, Overall and findings guards still apply. Rejected responses add `responseValidation.scoreStructure` with fixed category/token classes and capped counts only, never response text or score values. These diagnostics do not infer or restore scores for earlier attempts. The [assessment harness](../apps/web/lib/__tests__/fixtures/review-assessment-harness.ts) covers formatting compatibility, malformed responses and diagnostic redaction.

The [system prompt output format](../apps/web/prompts/SYSTEM_PROMPT.md#findings-summary) owns the findings-summary table and JSON contract. For compatibility, a standalone `> ⚠️ **Conflict Risk**:` advisory, including blockquote continuation lines, may follow that table; duplicate tables/headings/markers, malformed rows and mismatched counts still fail. The [conflict prompt](../apps/web/prompts/CONFLICT_DETECTION.md) owns advisory placement for new responses. Structural failure reasons contain fixed diagnostic text rather than response excerpts.

The existing missing-findings recovery call retains separate digest-only request, model/provider, policy/template, response and completion records. Interrupted or unobserved recovery remains explicit. Recovery never upgrades the primary assessment or supplies missing source coverage. Before parsing or merging findings, recovery validates the entire raw payload: one JSON array, optionally enclosed in a complete `json` fence or a single findings-marker pair (which may contain that fence). Extra content, multiple envelopes or any invalid entry reject the entire recovery set; there is no Markdown fallback. Valid primary findings remain available, including in an unscored verification-gap report when rejected recovery content triggers [excluded-input containment](#claims-about-excluded-input).

## Results and history

GitHub maintains one tracked summary comment per PR, updating it for queue, progress and final results. Re-reviews reuse the stored summary ID; existing historical comments are left intact. The summary has one plain Review history link to `/review-attempts/{id}`. The readable page shows the selected immutable report and metadata for up to ten recent reviews of the same PR, with dates, commits and an explicit Download JSON action. Signed-out visitors return to their requested review after login. The page enforces blocked-account and required-password-change protections; page access requires an undeleted membership in a nondeleted, nonbanned organisation and an active repository. The GitHub comment does not show a blanket access warning. Existing `/api/review-attempts/{id}` links redirect browser HTML navigation to the page unless an Authorization header or `?download=1` requests the export. JSON clients retain the authenticated immutable export of the complete manifest and final report, using organisation membership or that organisation’s API token. Authentication, account-hold responses and tenant filtering apply; exports and redirects are private and uncached. Optional rich rendering shares the publisher’s [Markdown admission limits](#limits-and-follow-up-work). Larger or more complex saved text is shown escaped in a scrollable plain-text view; stored bytes and JSON downloads are unchanged. Detailed inline findings still use native GitHub review threads.

Summary publication locks the PR row while checking head/request identity and writing the provider comment, so a concurrent admitted request cannot be overwritten by an older publisher. Final publication also checks the saved result body; late progress cannot replace a completed result. Authentication resolves before locking, provider requests share a ten-second deadline, and the transaction has a twenty-second timeout. Only a confirmed missing-comment 404 creates a replacement; other failures propagate without creating another summary. No schema or review-input changes are required.

Coverage states are `supplied`, `partial`, `omitted`, `excluded`, and `unavailable`. The manifest also records expected/known file counts, pagination completeness, provider, head/base SHAs and limitations. `supplied` means all known changed text hunks were included in model input; it is not a guarantee that the model found every defect.

If a required file/hunk or part of the inventory is unavailable, the report says **Review incomplete**, omits the overall quality score, and the native check fails even when zero blocking findings were found. Severity thresholds still govern findings for fully covered reviews. Useful findings from incomplete reviews remain visible. This changes the result of an incomplete review; it does not change GitHub branch protection settings.

`ENABLE_INTERNAL_CLI` controls delegation of oversized GitHub reviews and defaults to `false`; with delegation disabled, the standard engine uses the bounded input described above. A completed large-review worker result currently carries prose without an independently verified file inventory. Its coverage is therefore unknown and cannot produce a passing complete-review check. The queued request carries `attemptId`, pinned `headSha` and `baseSha`, the original `checkRunId`, and `reviewRequestVersion`. The worker result protocol adds exactly one optional `reviewRequestVersion` field: a producer must echo the queued value unchanged on success and failure, never substitute a freshly fetched current version. The preserved companion patch still needs this version-field extension by its owner; this checkout does not modify the archived worker. Results without a valid originating version remain incomplete and archived without promoting current state, while their original checks can still be finalized. The consumer archives legacy results lacking identity without promoting the current report or touching a check. Correlated delayed results complete only their original check and cannot replace a newer head's report. When a correlated large result no longer matches the current head, request version or saved report, its recorded outcome is `superseded` rather than `failed`. An already published outcome remains `published` even if a replacement request arrives afterward. This release does not change the worker's activation setting or pretend its prose proves coverage.

Each finalized attempt has an append-only `ReviewAttempt` record. Identical redelivery reuses the archive without re-promoting it; a reused ID with different PR, revision, body or semantically different coverage is rejected. Large-result archives commit before final comments or native completion. Separate `ReviewAttemptDelivery` checkpoints track the main comment, summary and completed delivery; a lease serializes concurrent delivery and expired leases can be reclaimed. Saved but unfinished publication resumes only against the same current report. Successful checkpoints prevent ordinary retries from duplicating comments; as with other provider calls, a process crash or lost acknowledgement after remote publication can still cause an at-least-once duplicate. Correlated redelivery retries the original native check before returning; transient check failures propagate to the existing queue retry mechanism. Empty-input finalization explicitly clears current findings under the same revision guard. Bitbucket and GitLab retain separate revision-labeled attempt comments. Promotion of the current comment pointer and status uses an atomic head-and-request-version predicate. Saving a final attempt archives its body even when stale; current report promotion and findings replacement share a short transaction whose conditional PR update locks the row before replacing findings. Model generation and provider publication run outside the archive transaction; GitHub summary publication uses its separate bounded row-lock transaction described above. GitHub review records carry the originating commit ID. Request admission reads the provider head after taking a database snapshot and conditionally replaces that snapshot. A competing write forces a fresh provider check; stale webhook heads cannot clear a newer report. Same-head completed reviews may be deliberately requested again. Every persisted review request atomically increments `PullRequest.reviewRequestVersion` (new PRs start at 1; existing rows migrate to 0). Dashboard request/status events and initial rows carry this version and the head SHA. Consumers accept only newer request versions and require exact version/head equality for status updates; duplicate request delivery cannot reset a completed row. Storage, comment pointers and reviewer status changes use the same version predicate. Status updates require the same repository, PR identity and known head as the dashboard row; unknown status events are ignored, and requests without a head cannot replace a row with a known head. An older head therefore retains its attempt without replacing the newer head's comment, findings, status, or report. For record navigation, export and access rules, see the start of [Results and history](#results-and-history). Repository/organization removal follows the existing cascading deletion policy.

New large-review failures use a fixed public message or an allowlisted producer stage. A private database-only fingerprint distinguishes different errors for the same attempt and is excluded from the review-record API. A retry of an already archived older failure retains its immutable body; previously archived or externally published content is not cleaned up. Allow in-flight large-review jobs to finish on the old consumers before the new consumers take over.

Apply the `20260910223000_review_coverage_attempts`, `20260911090000_review_request_version`, `20260911110000_review_attempt_delivery` and `20261108235500_large_review_failure_fingerprint` database migrations before deploying code that uses them. No migration is executed by a review request.

## Claims about excluded input

Hosted PR requests include a machine-authored changed-file visibility manifest, including policy-excluded paths. Supplied input describes changed hunks, not necessarily complete files. Exclusion and missing review context do not establish a repository defect.

A bounded presentation guard checks the initial response and recovered findings for explicit English absence claims referencing known excluded paths, including auxiliary finding prose, claims anchored to another supplied file and score notes based on unseen excluded input. Full paths use exact case-sensitive identity; a basename is accepted only when unique in the changed-file inventory. Ordinary visibility disclosures and claims about supplied paths remain unchanged. Paths marked removed or deleted by the provider are exempt: provider-observed deletion supplies evidence of absence. This guard does not fetch excluded contents or change exclusions.

If a claim is withheld, the original holistic summary, score and checklist cannot be trusted to be consistent with the retained findings. The report replaces them with an unscored verification gap and retains unrelated parsed findings for the existing confidence, validation and severity stages. Malformed or multiple findings blocks do not become a valid findings set through this rewrite. The original provider response digest and completion receipt remain in the immutable attempt; input completeness is preserved and the assessment/native check stays incomplete. Score reconciliation cannot manufacture a passing assessment.

If assessment already failed validation, that original failure remains first in its diagnostic; containment appends its reason once. Recovered findings use the same boundary and retain their separate provider receipts.

This is containment for explicit known-path assertions, not general semantic verification. Implicit subjects, arbitrary paraphrases, other languages, unchanged paths absent from the inventory and independently verified source supplements require further evidence contracts and versioned model evaluation. The legacy local-review protocol has no coverage manifest and is outside this hosted guard. Synthetic regressions validate the emitted request, containment and publication interfaces; they do not prove model interpretation.

## Author comments and source supplements

The trigger comment is sent once as untrusted context, outside system instructions. The receipt records received/supplied character counts and any truncation. Source excerpts and claimed hashes in comments are not independently verified and do not add changed-hunk coverage. This fixes duplicated 59k-character supplements and makes the current trust boundary explicit; it does not establish a new verified-source upload protocol.

## Limits and follow-up work

The main model review uses the `MAX_DIFF_CHARS` budget defined in [`diff-truncate.ts`](../apps/web/lib/diff-truncate.ts), defaulting to 350,000 characters. An explicit positive environment override remains supported. This is a changed-source ceiling, not a token allowance for the entire prompt: retrieved context, instructions and output also consume the selected model's context. Provider pagination and retained patches remain bounded. Eligible default-budget overflow can use [measured complete review admission](measured-review-capacity.md). Input that remains beyond the applicable allowance produces an incomplete result; there is no automatic multi-batch review or model fallback.

Retries after incomplete, malformed or unrecorded assessments perform a full review. Restricted follow-up mode requires complete current input and the latest immutable attempt to belong to the immediately preceding request, with a complete model assessment, the same non-null base revision and supplied coverage of every currently eligible path. Its assessment receipt must record successful completion, preserved input, matching model identity, a provider and valid request, response, policy and template digests. The guard never searches back for an older successful attempt. The positive “No new issues detected since the last review” banner also requires a complete current assessment; zero findings from invalid output cannot produce it. A previous comment alone cannot establish that the source was assessed. Missing, contradictory or unavailable evidence, a request-version gap or a newly eligible path keeps the full assessment, including non-critical findings and inline publication at previously commented locations.

Further work can add bounded multi-pass scheduling and verified source-supplement retrieval on top of this coverage contract. Those features must merge coverage only for exact-revision, actually supplied hunks; summaries, generated labels and unverified comments must never turn missing source into complete coverage.

The original Maestro #801 regression is verified privately against immutable evidence; the public test uses a synthetic 203-file contract case so private source is not copied into this repository. The tests exercise provider pagination, emitted model input, hunk budgeting, score/check outputs, append-only attempt storage and the actual authenticated retrieval handler.

The assessment validator accepts plain JSON and a complete `json` code fence inside the findings markers. Malformed payloads and per-severity summary/payload mismatches remain incomplete before score reconciliation, even if later findings recovery fails. Standard reports processed by presentation finalization contain exactly one last-reviewed footer pinned to the input head; no-model and legacy worker results retain their available revision identity in the coverage manifest. The adapter harness captures the final comment through production stripping, score reconciliation and `updatePullRequestComment`, with fetch fully mocked and a synthetic originating native-check envelope. This exercises adapter, storage and comment publication boundaries; it is not full `processReview` orchestration or live publication.

Archived coverage previews budget the escaped row text, including HTML entity expansion, to 12,000 characters and at most 100 paths; the immutable manifest retains every path. GitHub removes the inventory before applying its 64,000-character publication cap. If the comment still exceeds that cap, a canonical report is reduced to its attempt reference, coverage status, heading, scores, assessment reason, archive link, truncation disclosure and full-head footer; findings remain in the archive. The [history section](#results-and-history) is retained when its generated section fits within 3,000 characters. Complete assessments retain the score table with bounded notes; incomplete assessments omit category scores and retain an explicit reason and nonnumeric Overall. The archive retains the unabridged report. Oversized and Turkish fixtures exercise the actual mocked PATCH publisher.

The archived coverage preview uses an ordinary Markdown heading and table, without a `details`/`summary` HTML wrapper. GitHub publication omits that inventory from the conversation: it shows the coverage totals, any unassessed warning, and `Full coverage and review record: <URL>` with a plain URL and an Octopus sign-in notice. Findings and scores remain subject to the size and assessment rules above. Bitbucket and GitLab retain the ordinary Markdown preview. In the archived preview, the attempt UUID and archive URL appear as plain text; head/base details are on the following line so strict consumers do not confuse a URL with adjacent inline code. Shortened GitHub comments retain the coverage status and attempt reference from both this layout and older stored reports that used a Markdown link, preserving the distinction between missing input and an invalid or unavailable assessment. This presentation change preserves the coverage and assessment rules above; it does not make the displayed manifest an independently verified completeness or attempt-binding guarantee.

GitHub publication renders raw pipes in supported same-line prose code spans as code chunks separated by escaped visible pipes. This keeps the literal text readable by strict evidence consumers without inserting visible backslashes. Source-offset edits preserve tables, fenced and indented code, links, HTML, quoted blocks, headings and multiline spans. Optional parsing is admitted only for inputs of at most 64,000 UTF-16 code units and 2,048 aggregate ASCII punctuation characters; inputs exceeding either limit remain byte-identical at this step. These conservative limits address measured parser slowdowns, not every possible Markdown complexity case. Unsupported output can still fail a strict reader. The original report and assessment stay in the immutable record; size limiting still runs after this presentation step.

Report preparation separates machine findings from presentation before repairing fences, removing empty diagrams, sanitizing Mermaid or normalizing scores and footers. The production preparation helper checks payload identity and summary consistency before filtering; finalization checks payload identity again before scoring and publication. Corruption makes the assessment incomplete without treating deliberate downstream filtering as payload corruption. The mocked adapter/archive/PATCH harness executes these production preparation and finalization helpers, including critical findings after empty diagrams and fence-like finding descriptions; it does not exercise full reviewer orchestration. A separate harness invokes the production recovery helper through the mocked provider SDK and immutable archive boundary.

Findings integrity uses the same strict JSON and per-severity count-table validator as initial assessment, independently of the Score section. The publication harness covers the [incomplete-input assessment contract](#assessment-completion-and-request-provenance) in ordinary and compact comments, plus a corrupted-payload control.
