# Review coverage and incomplete results

A completed job is not necessarily a complete PR assessment. Octopus records which changed text hunks it actually supplied to the reviewer, separately from findings and quality scores.

## Standard review input

The reviewer enumerates provider file metadata before allocating its model-input budget. GitHub file pagination is independent of the raw diff ceiling, so a large early fixture cannot erase the paths or patches of later source files. GitLab diff metadata and Bitbucket diffstat are paginated too. The provider revision is checked before and after fetching; changed head/base revisions abort the attempt instead of mixing input revisions.

Source, configuration and package/build scripts have priority over test fixtures and documentation. Whole files that fit are supplied first; remaining space can contain complete hunks from a larger file. There is no character cut through a hunk. File and hunk digests and ranges are retained in the coverage manifest. Each supplied hunk records `sha256` over its exact emitted text (including its hunk header and normalized trailing newline); `suppliedSha256` hashes the entire emitted file section, while `patchSha256` hashes the original provider patch. Provider patch omissions and mismatched hunk/change counts stay explicit.

Existing `.octopusignore` exclusions are recorded as repository policy. Curated default generated-file exclusions remain explicit. A repository's additional generated labels cannot silently hide source, tests, schemas or configuration; those remain accounted for. Excluded files are not claimed as reviewed.

## Assessment completion and request provenance

Supplied files alone do not establish a completed assessment. The final provider adapters report completion state and capture SHA-256 receipts over their actual SDK request payloads, after model-prefix, caching, thinking and text transformations. Each receipt records whether all requested message contents survived the transformation. The attempt retains these receipts, the selected model, policy/template digests, response-text digest and completion outcome; it does not publish raw prompts, credentials or private source.

A passing assessment requires a completed provider response, preserved request input and a valid report with its canonical score table and findings JSON. Empty, malformed, token-limited, interrupted, unknown-completion or unobserved responses stay incomplete and cannot publish a numeric Overall or successful native check. Useful findings remain available. Legacy/local bridges without underlying completion evidence stay unknown. Explicitly excluded-only input records a no-model disposition; it does not claim an assessment of the excluded content. Identical immutable retries remain idempotent; changing request, policy or outcome evidence conflicts with the original attempt.

The existing missing-findings recovery call retains separate digest-only request, model/provider, policy/template, response and completion records. Interrupted or unobserved recovery remains explicit. Recovery never upgrades the primary assessment or supplies missing source coverage.

## Results and history

Coverage states are `supplied`, `partial`, `omitted`, `excluded`, and `unavailable`. The manifest also records expected/known file counts, pagination completeness, provider, head/base SHAs and limitations. `supplied` means all known changed text hunks were included in model input; it is not a guarantee that the model found every defect.

If a required file/hunk or part of the inventory is unavailable, the report says **Review incomplete**, omits the overall quality score, and the native check fails even when zero blocking findings were found. Severity thresholds still govern findings for fully covered reviews. Useful findings from incomplete reviews remain visible. This changes the result of an incomplete review; it does not change GitHub branch protection settings.

`ENABLE_INTERNAL_CLI` controls delegation of oversized GitHub reviews and defaults to `false`; with delegation disabled, the standard engine uses the bounded input described above. A completed large-review worker result currently carries prose without an independently verified file inventory. Its coverage is therefore unknown and cannot produce a passing complete-review check. The queued request carries `attemptId`, pinned `headSha` and `baseSha`, the original `checkRunId`, and `reviewRequestVersion`. The worker result protocol adds exactly one optional `reviewRequestVersion` field: a producer must echo the queued value unchanged on success and failure, never substitute a freshly fetched current version. The preserved companion patch still needs this version-field extension by its owner; this checkout does not modify the archived worker. Results without a valid originating version remain incomplete and archived without promoting current state, while their original checks can still be finalized. The consumer archives legacy results lacking identity without promoting the current report or touching a check. Correlated delayed results complete only their original check and cannot replace a newer head's report. This release does not change the worker's activation setting or pretend its prose proves coverage.

Each finalized attempt has an append-only `ReviewAttempt` record. Identical redelivery reuses the archive without re-promoting it; a reused ID with different PR, revision, body or semantically different coverage is rejected. Large-result archives commit before final comments or native completion. Separate `ReviewAttemptDelivery` checkpoints track the main comment, summary and completed delivery; a lease serializes concurrent delivery and expired leases can be reclaimed. Saved but unfinished publication resumes only against the same current report. Successful checkpoints prevent ordinary retries from duplicating comments; as with other provider calls, a process crash or lost acknowledgement after remote publication can still cause an at-least-once duplicate. Correlated redelivery retries the original native check before returning; transient check failures propagate to the existing queue retry mechanism. Empty-input finalization explicitly clears current findings under the same revision guard. Each attempt creates its own revision-labeled progress/result comment; it never edits a predecessor attempt's comment. Promotion of the current comment pointer and status uses an atomic head-and-request-version predicate. Saving a final attempt archives its body even when stale; current report promotion and findings replacement share a short transaction whose conditional PR update locks the row before replacing findings. Model generation and provider publication run outside that transaction. GitHub review records carry the originating commit ID. Request admission reads the provider head after taking a database snapshot and conditionally replaces that snapshot. A competing write forces a fresh provider check; stale webhook heads cannot clear a newer report. Same-head completed reviews may be deliberately requested again. Every persisted review request atomically increments `PullRequest.reviewRequestVersion` (new PRs start at 1; existing rows migrate to 0). Dashboard request/status events and initial rows carry this version and the head SHA. Consumers accept only newer request versions and require exact version/head equality for status updates; duplicate request delivery cannot reset a completed row. Storage, comment pointers and reviewer status changes use the same version predicate. Status updates require the same repository, PR identity and known head as the dashboard row; unknown status events are ignored, and requests without a head cannot replace a row with a known head. An older head therefore retains its attempt without replacing the newer head's comment, findings, status, or report. The report links to `/api/review-attempts/:id`, which returns the complete manifest and final report as a JSON download. Access requires an active membership in the repository's organization or that organization's API token. Authentication, account-hold responses and tenant filtering apply; downloads are private and uncached. Repository/organization removal follows the existing cascading deletion policy.

Apply the `20260910223000_review_coverage_attempts`, `20260911090000_review_request_version` and `20260911110000_review_attempt_delivery` database migrations before deploying the application. No migration is executed by a review request.

## Author comments and source supplements

The trigger comment is sent once as untrusted context, outside system instructions. The receipt records received/supplied character counts and any truncation. Source excerpts and claimed hashes in comments are not independently verified and do not add changed-hunk coverage. This fixes duplicated 59k-character supplements and makes the current trust boundary explicit; it does not establish a new verified-source upload protocol.

## Limits and follow-up work

The main model review uses the `MAX_DIFF_CHARS` budget defined in [`diff-truncate.ts`](../apps/web/lib/diff-truncate.ts), defaulting to 350,000 characters. An explicit positive environment override remains supported. This is a changed-source ceiling, not a token allowance for the entire prompt: retrieved context, instructions and output also consume the selected model's context. Provider pagination and retained patches remain bounded. Material beyond the allowance produces an incomplete result; there is no automatic multi-batch review or model fallback.

Retries after incomplete, malformed or unrecorded assessments perform a full review. Restricted follow-up mode requires complete current input and the latest immutable attempt to belong to the immediately preceding request, with a complete model assessment, the same non-null base revision and supplied coverage of every currently eligible path. Its assessment receipt must record successful completion, preserved input, matching model identity, a provider and valid request, response, policy and template digests. The guard never searches back for an older successful attempt. A previous comment alone cannot establish that the source was assessed. Missing, contradictory or unavailable evidence, a request-version gap or a newly eligible path keeps the full assessment, including non-critical findings and inline publication at previously commented locations.

Further work can add bounded multi-pass scheduling and verified source-supplement retrieval on top of this coverage contract. Those features must merge coverage only for exact-revision, actually supplied hunks; summaries, generated labels and unverified comments must never turn missing source into complete coverage.

The original Maestro #801 regression is verified privately against immutable evidence; the public test uses a synthetic 203-file contract case so private source is not copied into this repository. The tests exercise provider pagination, emitted model input, hunk budgeting, score/check outputs, append-only attempt storage and the actual authenticated retrieval handler.

The assessment validator accepts plain JSON and a complete `json` code fence inside the findings markers. Malformed payloads and per-severity summary/payload mismatches remain incomplete before score reconciliation, even if later findings recovery fails. Standard reports processed by presentation finalization contain exactly one last-reviewed footer pinned to the input head; no-model and legacy worker results retain their available revision identity in the coverage manifest. The adapter harness captures the final comment through production stripping, score reconciliation and `updatePullRequestComment`, with fetch fully mocked and a synthetic originating native-check envelope. This exercises adapter, storage and comment publication boundaries; it is not full `processReview` orchestration or live publication.

Coverage previews budget the escaped row text, including HTML entity expansion, to 12,000 characters and at most 100 paths; the immutable manifest retains every path. If a final GitHub comment still exceeds the existing 64,000-character cap, publication emits a compact review with the attempt identity, canonical heading, archive link, truncation disclosure and full-head footer. Complete assessments retain the score table with bounded notes; incomplete assessments omit category scores and retain an explicit reason and nonnumeric Overall. The archive retains the unabridged report. The [system prompt output format](../apps/web/prompts/SYSTEM_PROMPT.md#findings-summary) owns the findings-summary table and JSON contract, including zero-finding results and configured-language commentary. Oversized and Turkish fixtures exercise the actual mocked PATCH publisher.

The coverage preview uses an ordinary Markdown heading and table, without a `details`/`summary` HTML wrapper. The attempt UUID and archive URL appear as plain text; head/base details are on the following line so strict consumers do not confuse a URL with adjacent inline code. Shortened GitHub comments retain the attempt reference from both this layout and older stored reports that used a Markdown link. This presentation change preserves the coverage and assessment rules above; it does not make the displayed manifest an independently verified completeness or attempt-binding guarantee.

Report preparation separates machine findings from presentation before repairing fences, removing empty diagrams, sanitizing Mermaid or normalizing scores and footers. The production preparation helper checks payload identity and summary consistency before filtering; finalization checks payload identity again before scoring and publication. Corruption makes the assessment incomplete without treating deliberate downstream filtering as payload corruption. The mocked adapter/archive/PATCH harness executes these production preparation and finalization helpers, including critical findings after empty diagrams and fence-like finding descriptions; it does not exercise full reviewer orchestration. A separate harness invokes the production recovery helper through the mocked provider SDK and immutable archive boundary.

Findings integrity uses the same strict JSON and per-severity count-table validator as initial assessment, independently of the Score section. A completed valid response over partially supplied input retains its provider-completion state, reason and provenance; coverage remains incomplete, Overall remains unassessed and the native check fails. Withholding a score is not findings corruption. The publication harness covers partial input with completed responses in ordinary and compact comments, plus a corrupted-payload control.
